  起因是"效果差"这件事在文档里已经拆成了**分层归因**(关①检索侧 / 关②门槛 / 关④归属,

## 供应商模型别名与成本口径(2026-09-25)

- **D-71 单价表不能照抄官方价目表:项目调用的 `deepseek-chat` 已过公告停用日期、
  且不在当前官方价格表内 —— 本轮**不填**单价表,`cost_basis` 维持 `unknown`**:
  起因是"把 131 条 `unknown` 变成 `estimated`"这个改进看起来只是往 `.env` 加两个值。
  查证后发现填不了,理由如下(全部有据,非推测)。

  **官方公告(api-docs.deepseek.com/updates,查于 2026-09-25)**
  - 2026-04-24:`deepseek-chat` 与 `deepseek-reasoner` 两个旧别名**将于三个月后
    (2026-07-24)停用**;过渡期内分别指向 `deepseek-v4-flash` 的非思考/思考模式。
  - 2026-09-10:V4.1-Flash 发布,模型名改为 `deepseek-flash`;上一代 V4 Flash 与
    V4 Flash Vision Exp 已退役,旧名 `deepseek-v4-flash` 仅**临时**路由到 V4.1 Flash。
    公告里**只字未提** `deepseek-chat` 现在指向什么。

  **当前官方价格表(api-docs.deepseek.com/quick_start/pricing)只列两个模型**:
  `deepseek-flash` 与 `deepseek-v4-pro`,**没有 `deepseek-chat`**。且计费是
  **四维**(缓存命中/未命中 × 峰/谷),谷价 = 峰价一半;峰时段为
  01:00–04:00 与 06:00–10:00 UTC 的周一至周五(不含中国法定假日)。
  仅作参考(¥/$ 与币种见下方未决项,单位均为 /1M tokens,美元):
  `deepseek-flash` 缓存命中 峰 $0.006 / 谷 $0.003;缓存未命中 峰 $0.3 / 谷 $0.15;
  输出 峰 $1.2 / 谷 $0.6。

  **实测:该别名今天仍在服务,但没有任何价格依据**
  `model_run` 中今日(2026-09-25 14:27Z)仍有 2 次 `deepseek-chat` 调用
  `status=succeeded`(`tokens_in/out` = 256/13、286/27)。→ 别名未失效,但它
  既不在官方价目表内,公告也未给出映射,**无法确定它按哪个价点计费**。

  **项目成本模型也表达不了现在的计费**
  `app/core/config.py:32-35` 只有两个平坦单价 `LLM_PRICE_PER_1K_IN/OUT`;
  代码只读 `prompt_tokens`(`app/ai/deepseek_provider.py:157`),**未区分**
  缓存命中的 `prompt_cache_hit_tokens`。四个价点压成两个平坦值必然失真。

  **结论**:任何数字都属猜测(违反纪律 1「禁止猜测/编造」),故不填。三个候选方案,
  等作者定:
  - **A. 只填两个峰价**(把 `unknown` 变成"保守上界 estimated"):最省事,与既有
    `estimate_cost()`「发出前按最大输出预留上界」的口径一致;但价目对应 `deepseek-flash`,
    而项目调的是 `deepseek-chat`,属**未验证的映射**。
  - **B. 先把 `DEEPSEEK_MODEL` 切到 `deepseek-flash`,再按官方价填**:价格可溯源、
    同时消除"别名随时可能失效"的隐患;代价是 LLM 行为改变,**现有评测基线
    (全部基于 `deepseek-chat`)需重跑**,按"一次只改一种策略"要单独一轮。
  - **C. 扩成本模型支持四价点 + 缓存命中 token**:最准,工作量最大,需迁移与测试。

  **另一个填价前必须先定的口径**:字段名是 `cost_cents`(分),但 `config.py` 注释写的是
  「货币 / 1K tokens」而**未指定币种**,官方价目是美元 —— 直接填美元数字会让
  `cost_cents` 名实不符。建议顺带把字段/注释的币种明确下来。未决。

## 前端界面缺陷与可复跑性(2026-09-25)

- **D-70 会谈详情页"一直在跳":终态任务被重复起轮询,轮询自我触发成无界刷新**:
  用户报告"人工转写那一页一直跳来跳去"。**不是显示问题**。前端 `renderRecordings()`
  对**每一条**录音无条件调 `pollJob(job_id)`,而 `pollJob()` 会立刻执行一次 `tick()`;
  任务已是终态(`succeeded`)时,`tick()` 走"已结束"分支又调 `renderRecordings()` →
  又 `pollJob()` → **无界自我刷新**。每轮重建 `#jobs` 与 `#minutes` 的整块 DOM,而
  `.grid` 是 `grid-template-columns:1fr 1fr` —— 重排把同行的「2. 人工转写导入」卡
  推上推下,**用户看到的是第 2 张卡在跳,根因在第 1 张与第 3 张卡**。
  现场证据:uvicorn 访问日志里 `GET /meetings/1` 与 `GET /meetings/1/minutes` 成对无限刷。
  离线量化(`.run/repro_poll_loop.mjs`:Node `vm` + 最小 DOM/fetch 桩,只调
  `renderRecordings()`;**未入仓**,见本小节末尾未决项):

  | 场景 | 改前 | 改后 |
  |---|---|---|
  | 任务已终态(演示数据常态) | 300ms 内 **501 次**(触发上限保护) | **0 次** |
  | 任务运行中,第 4 次轮询时转终态 | 300ms 内 **501 次** | **6 次**,随后停止 |

  场景 1 的"0 次"只覆盖 `renderRecordings()` 这条路径(数据已在响应里,无需再请求);
  真实打开详情页另有 `openMeeting` 的 `GET /meetings/{id}` 与 `loadMinutes()` 的
  `GET /minutes` 各一次,共 2 次请求后即静止。
  场景 2 用于确认"进度实时刷新"这个正常功能没被一起砍掉:4 次 `/jobs` 轮询
  (0/1500/3000/4500ms)+ 转终态后各刷新一次 `/meetings`、`/minutes`。
  修法(单一变量):新增一份终态判据 `TERMINAL_JOB = new Set(["succeeded","failed"])`,
  同时用于"停止轮询"与"是否重新起轮询",已终态的任务不再起轮询 —— 理由与 D-65/D-69 同源:
  同一判据写在两处就会漂移。
  `app/web/index.html` 的 `app.js?v=` 手动缓存号随之从 `20260923g` 升到 `20260925a`。
  验证:`pytest -q` → 141 passed / 3 skipped(纯前端改动,后端无回归);
  `curl /static/app.js` 实际响应已含 `TERMINAL_JOB`;首页引用的版本号已是 `20260925a`。
  回滚:把 `renderRecordings` 末行恢复为 `recs.forEach((r) => r.job_id && pollJob(r.job_id));`。
  已实现。

  过程值得记下:**第一版弱闸("问题型号只要出现在任一引用里就行")在冻结 dev 的 mock
  基线上误报仍然是 1** —— 因为语料里另有一句"X300 型号的保修期是多久?"确实提到了 X300,
  但它回答的不是注册证日期。若不是回去重跑了基线,我会把这条"看起来合理"的闸当成功提交。
  收紧后的规则:引用中至少要有一段**同时**满足①含问题点名的型号 ②含问题所要的那类线索
  (日期/时长/数量/负责人,分类与 mock 线索规则同一口径),否则判证据不足;
  问题没点型号时不介入(避免误伤"谁负责培训"这类题)。
  实测(单一变量,基线 = `mock_after_gate.json` 前后各跑一次):
  ① 冻结 dev 6 题 mock 路径:无答案正确拒答 **0.5 → 1.0**,型号错配误报 **1 → 0**,
  4 道可答题命中率 1.0 不变(无误伤);② 扩充 dev 24 题真模型路径
  (bge-m3 + DeepSeek):**五项指标与逐题对错完全不变**(其两道误答是"硬镜/蒸发罐"
  部件名词,不属型号代号;而带型号的负例本来就被模型拒了)—— 既无收益也无回归;
  ③ 服务层测试断言的是**层级**:`relevant_candidate_count > 0` 却仍判不足,
  证明拦住它的是归属闸而不是"没检索到"。
  结论:**保留**,但收益范围如实写清 —— 它只管型号代号,部件级归属(硬镜/蒸发罐)
  仍靠模型判断,那两类误答还在。回滚方式:删掉 `_clue_asked`/`focus_mismatch`
