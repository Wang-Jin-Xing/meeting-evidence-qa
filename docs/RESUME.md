## 版本一:精简(简历正文,4 条)

**医疗机构—厂商会谈 智能纪要与证据问答系统**(个人项目,FastAPI / PostgreSQL+pgvector / Docker)

- 设计并实现**可回溯的证据链**:录音原件只读、转写与纪要均为**只追加的版本树**
  (含人工校对血缘 `segment_mapping`),用**双发布指针**分离"当前展示版本"与"当前检索版本",
  使索引重建窗口期内不可能检到未发布内容;纪要确认信息记录在**具体版本行**上
  (谁确认、何时确认),编辑后必须重新确认,并发编辑以 409 拒绝而非静默覆盖。
- 实现**独立 worker 进程 + 数据库租约(fencing token)**的可靠流水线:四阶段幂等推进、
  失败退避、租约过期被其他 worker 接管后旧持有者提交被拒;
  以真实子进程做故障注入与并发接管测试,进程被杀后任务可恢复且不重发已提交分片。
- 建立**多租户权限注入**模型:机构归属仅由服务端从 JWT 解析,可见性条件写入检索 SQL
  (机构等值 + 可见会谈子查询 + 显式会谈限定 + 发布指针匹配),无权与不存在统一 404;
  音频字节经鉴权接口 + HTTP Range 提供,不暴露静态目录;24-bit 原件按需生成
  16-bit **派生播放副本**(原件不改,副本帧数/采样率/声道与原件校验一致),界面可按引用切片回放并到点自停。
- 接入真实模型并**用实验区分故障层次**:本地 faster-whisper + bge-m3 + DeepSeek 全链路跑通真实录音;
  以人工确认的 6 处校对为金标做 A/B 双链路对比,量化出"校对使 5 问相似度全部提升(Δ +0.03~+0.13)
  且修掉答案错字",同时把 2 个仍失败的问题**从"识别错误"改判为"阈值偏高"**(0.6566 vs 0.66,单录音 5 问)。
  调用台账区分 `estimated / provider_reported / unknown` 三态成本,未知**不以 0 记账**。

## 版本二:一句话(简历标题行 / 自我介绍)

"做了一个会谈纪要与证据问答系统,重点在**让每句结论可回溯到原始录音片段**:版本只追加、
检索只认发布指针、worker 带租约可接管、成本三态不填 0,并用 A/B 实验把'模型不行'和'阈值不行'分开。"
